# 校园版、企业版、金融版账号隔离

版本值沿用项目现有命名：`school`、`enterprise`、`finance`。

## 生效行为

- 同一个手机号、邮箱、用户名和微信身份可在三个版本分别注册，各版得到独立用户 ID、密码、积分和资料。
- 账号归属由服务端 `APP_EDITION` 决定，客户端不能指定归属。
- 当前版本找不到账号时提示先注册当前版本；微信首次进入另一版需要验证手机号并完成该版注册。
- 注册、重置密码、微信绑定的短信校验场景按版本和用途区分。
- JWT 绑定版本及 audience；旧版无版本 JWT 失效，用户需重新登录。前端登录缓存也按版本分开。
- 用户资料、管理端用户列表、积分、问答记录、档位调整和用户删除按账号所属版本限制访问。

## 先核对旧账号，不能猜归属

旧数据库没有注册版本字段时，无法仅凭手机号判断归属。历史聊天中出现过某一版本也不能证明它最初注册于该版。

从实际部署目录、使用对应数据库配置运行只读检查：

```sh
node scripts/audit-account-editions.mjs --output account-edition-audit.json
```

检查工具不初始化数据库、不修改账号，不输出密码哈希或手机号。报告列出账号 ID、用户名、已有归属和历史使用版本，仅供人工核对。输出文件必须不存在，防止覆盖已有核对结果。

若连接认证失败，应先校正部署环境的数据库连接配置，不能据此将所有账号归到校园版。

确认后选择以下一种配置：

1. 确认整个旧数据库只属于某一版，在其服务环境设置 `LEGACY_ACCOUNT_EDITION=school`（或 `enterprise`、`finance`）。独立数据库分别配置各自版本。
2. 旧账号混合，提供以用户 ID 为键的 JSON 文件，并设置 `ACCOUNT_EDITION_MAP_FILE` 为文件绝对路径：

```json
{
  "已确认校园版的用户ID": "school",
  "已确认企业版的用户ID": "enterprise",
  "已确认金融版的用户ID": "finance"
}
```

映射优先于默认值；混合数据库建议不设置默认值，避免漏填账号被错误归类。若使用默认值，该值只适用于映射未覆盖的旧账号。

**未确认归属的旧账号会使首次迁移中止并回滚，不会自动归到先启动的版本，也不会复制到三个版本。** 已有明确 `edition` 的账号会保留原值。迁移保留原用户 ID、密码哈希、积分和关联记录；历史记录不会自动复制给另一个版本的新账号。

## 升级顺序

1. 备份实际业务数据库及配置，保存核对后的版本映射。
2. 停止所有连接同一数据库的旧版 API 进程，避免旧程序在新约束下继续写入无版本账号。
3. 配好旧账号归属，更新代码，执行 `npm ci` 和 `npm run build:all`。
4. 先启动一个 API 进程完成迁移，确认成功，再启动另外两个版本。PostgreSQL 迁移有事务和并发锁；SQLite 迁移在事务内重建约束并验证外键。
5. 部署各版前端产物，确认旧账号仅能登录其归属版本；在另外两版分别注册后再登录。

新空库无需旧账号配置。成功迁移记录版本号，后续启动不会重新分配旧账号。若需回滚旧程序，应同时恢复迁移前数据库备份；不能直接在新库运行旧认证程序。

## 验证

```sh
npm test
npm run build:all
```

PostgreSQL 集成测试只应指向可丢弃的空测试数据库，绝不能使用业务库：

```sh
ACCOUNT_EDITION_TEST_DATABASE_URL=postgresql://user:password@127.0.0.1:55439/testdb node --test backend/test/accountEditionIsolation.test.js backend/test/accountEditionMigration.test.js
```

测试覆盖同身份三版注册、同版重复注册、跨版登录凭证和管理操作拒绝、微信独立绑定、短信版本/用途隔离、旧数据迁移保留、未确认归属回滚及重复启动。
